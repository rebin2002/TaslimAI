# Public free-tier provider-cost firewall — integration handoff

**Status: P0 pre-public-beta gate; NOT integrated; NOT deployable as a firewall.** This isolated owner-safe PR adds a pure, fail-closed policy, a reservation-ledger contract with deterministic tests, and a standalone quota/unavailable notice with render tests. It does not register the policy in the API, mount the notice in any page, change routes/workers, create a durable database store, alter production configuration, or protect any currently reachable provider call. Keep public free-tier generation on hold until the integration and release gates below are completed on an owner-approved, exact reviewed HEAD.

## Why this gate exists

At the reviewed `main` HEAD (`c7622a13142ba85c3009955fbfafb2af0469f903`), the API production configuration has `Billing.CustomerChargingEnabled=false`, `UsageControls.GuardrailsEnabled=false`, and `GenerationBudget.Enabled=false`. Production `GenerationCostPricing` has no provider rates (`Version`, `EffectiveAtUtc`, and `Source` are null and `Providers` is empty). The seeded Free plan's 1,000 monthly customer credits are not provider-cost funds. Disabling customer debits therefore does not prevent a visitor's request from reaching a paid provider; with missing pricing, this policy must reject rather than infer zero cost.

The live route surface includes Chat/SSE, image, research, document, presentation, social, music, voice, video, Movie, upscaling, and background job execution. A gate only in a UI, controller preflight, or job-creation path is insufficient: every provider attempt, retry, SSE call, callback-triggered action, and worker execution needs a reservation immediately before dispatch.

## What this change supplies

`apps/api/Usage/PublicFreeTierProviderSpendPolicy.cs` defines an internal server-side admission request, a UTC-window exposure snapshot, a pure policy evaluator, and the `IPublicFreeTierSpendLedger` contract. The policy is off by default and returns service-unavailable when disabled or misconfigured; it never fails open. It requires an authenticated active account, confirmed email by default, a server-verified active workspace membership, and the server-derived Free plan. The request identity/plan/workspace/capability are not HTTP-bindable inputs.

Conservative defaults are 3 chat messages per user per UTC day, 10 per UTC ISO week, 2,000 input tokens and 512 output tokens per request, and estimated-cost ceilings of $0.10/user/day, $0.50/user/month, $0.25/workspace/day, $1/workspace/month, $1/global/day, and $5/global/month. Only `TextChat` is allowlisted by default. The implementation hard-denies image, video, voice, music, short-form clips, background provider jobs, unknown, and arbitrary provider routes even if they are accidentally added to configuration; only code-supported chat or low-cost lookup capabilities can be considered for later allowlisting after separate pricing, bounds, route coverage, tests, and review. These dollar amounts constrain estimates/reservations, not guaranteed provider invoices or usage charges.

The pure evaluator requires versioned USD pricing, matching fresh UTC-window/scope snapshots, and zero unknown-cost records. It bounds token input/output, returns explicit 401/403/413/429/503 decisions and UTC retry times, and performs overflow-safe spend comparisons. The user message/spend exposure is intended to aggregate across every workspace for that user; the global exposure spans every free account. Customer credits remain a separate ledger and are deliberately absent from the policy.

`apps/api.Tests/PublicFreeTierProviderSpendPolicyTests.cs` tests the policy and exercises the reservation contract with a test-only lock-based in-memory fake. That fake demonstrates intended atomic behavior, user-wide workspace aggregation, retry idempotency, unknown-cost holds, and settlement/refund semantics; it is **not** a production adapter and does **not** prove PostgreSQL, process, or multi-replica correctness. These tests make no paid-provider or network calls.

`apps/web/src/components/PublicFreeTierSpendNotice.tsx` and its focused test render accessible quota/reset and temporary-unavailability copy. The component deliberately accepts only a server-classified state and optional UTC retry time, makes no claim that customer credits were or were not deducted, and is **not mounted into an existing route or page** in this PR.

## Durable PostgreSQL reservation design (implementation blueprint; not yet integrated)

This section advances the durable-store design without claiming that the store exists. It is a proposal for a future adapter whose exact new-file reservation was rescinded by Release after the billing semantic review; no adapter/test file is authorized now. The current PR still contains no SQL adapter, schema, migration, dependency-injection registration, or provider call-site change. The store must not be activated until a canonical schema owner is assigned, the migration receives backup/restore and rollback review, and every provider-route/worker owner approves the call boundary.

### Durable records

- A reservation row should bind a server-generated reservation ID to authenticated `user_id`, authorized `workspace_id`, a canonical server-generated provider-attempt identity, server-derived capability, provider/model, immutable pricing version, USD estimate, SHA-256 request fingerprint, exact original UTC day/ISO-week/month keys, dispatch state, monotonic state version/fencing token, a correlation reference to the existing usage/attempt record, outcome state, actual USD when known, and UTC lifecycle timestamps. The attempt identity must be derived from the logical operation and provider-attempt number; the current internal `IdempotencyKey` can carry it until an owner-approved contract extension exposes those fields separately. Enforce uniqueness on `(user_id, workspace_id, attempt_identity)` (or the equivalent canonical key), and persist the fingerprint separately: same identity plus same fingerprint is a replay; same identity plus different fingerprint is a conflict, never a second reservation.
- A bucket row should use a composite key over `scope_kind` (`global`, `user`, `workspace`), canonical `scope_id` (a fixed non-null sentinel for global), `window_kind` (`day`, `iso_week`, `month`), and UTC `window_start`. Store `reserved_usd`, `actual_usd`, and applicable message counts separately as fixed-precision `numeric`/integer values with nonnegative checks; currency is USD for this version. Exposure is `reserved_usd + actual_usd`. User buckets aggregate across all workspaces; workspace buckets remain workspace-specific; global buckets include every public-free user. Daily and weekly message counters are user-scoped. Persist original bucket-window keys on every reservation so settlement after midnight or month rollover updates the original buckets, not newly derived current windows. Provider actuals may push exposure above a configured cap; record the full actual and block later reservations rather than rejecting settlement.
- A singleton global-gate row should hold a durable `unknown_reservation_count` and be locked by every reservation, dispatch-state, settlement, release, and reconciliation transaction. Any unresolved dispatched cost blocks all public-free admissions, matching the current policy contract's global unknown-cost hold. Completion/reconciliation events should be append-only with a unique `(reservation_id, completion_idempotency_key)` and payload fingerprint; same-key/same-payload is a replay, same-key/different-payload is a conflict, and a finalized known outcome rejects any new completion key.
- An unresolved outcome remains in `reserved_usd` at its full estimate and must not be silently expired or released. A stale lease, timeout, cancellation, socket error, or worker restart is not proof that the provider was never reached. Audit data must preserve attempt identity, original buckets, dispatch state, completion key/fingerprint, estimate, actual, and state transition for reconciliation.
- This ledger is a provider-exposure admission overlay, not customer-credit accounting. It must not read/write `CreditEntitlement` or `CreditLedgerEntry`, call `ICreditLedgerService`, or use `UsageTransactionAdjustment` as a provider-cost refund. Existing Chat `UsageTransaction` records and `GenerationProviderAttempt` records already hold actual/per-attempt cost facts; every free-tier reservation needs a correlation kind/ID to its corresponding canonical usage/attempt record. The route owners and accounting reviewer must designate one canonical actual-cost source and reconciliation path per capability. The exposure buckets are a control projection, not an additional billable expense: usage reports and global aggregates must not sum the same provider cost from both this overlay and the existing usage/attempt records.

### Atomic reservation transaction

1. Derive UTC day, ISO-week, and month keys once from the server clock. Build request identity, capability, plan, authorized workspace, price, and idempotency from trusted server state; do not accept a caller snapshot or client-selected user/workspace/plan/cost. The attempt identity must remain stable for a transport replay and change for a new provider attempt.
2. Begin one PostgreSQL transaction (row locks plus conditional updates under `READ COMMITTED` are sufficient if every writer follows this protocol; `SERIALIZABLE` is also acceptable with bounded retries). Lock the singleton global-gate row first. Resolve or create the reservation identity with a unique constraint; on an existing identity, compare the stored fingerprint and return the existing reservation only for an exact replay. Never include the fingerprint in the unique key. A failed/ambiguous commit must be resolved by querying that identity before any retry; never blindly reserve a second time.
3. Create missing current bucket rows with `INSERT ... ON CONFLICT DO NOTHING`, then lock all applicable rows in one canonical order on every code path: global day/month, user day/week/month, workspace day/month; sort same-class keys by window kind/start and scope UUID. Every reserve, dispatch-state, settlement, release, and reconciliation path must use the same order. A plain `SELECT ... FOR UPDATE` on a missing row does not lock the gap. The global-gate row intentionally serializes the small free-tier volume so cross-account caps and unknown holds have one durable ordering point.
4. Re-read bucket totals and global unknown count under those locks; evaluate the pure policy against this fresh in-transaction state, never a request-supplied or preflight-only snapshot. For each spend bucket, conditionally add the estimate only when `actual_usd + reserved_usd + estimate <= configured_cap`; atomically increment applicable user daily/weekly message counts. Any denial, constraint error, or partial update rolls back the reservation and every counter. Do not hold the transaction open during provider I/O.
5. Commit reservation plus all bucket increments before returning an admission token. Provider dispatch is forbidden until that commit succeeds; database unavailability, a missing schema/table, ambiguous transaction state, or unconfirmed reservation returns unavailable and causes zero provider calls. Retry only PostgreSQL `40001`/`40P01` with a fresh transaction and the same attempt identity, boundedly, before dispatch. Unique constraints and conditional updates are the final safety boundary.

### Settlement, failure, and release semantics

- Persist dispatch-start intent and the fencing/version token before handing a request to the network; a crash or ambiguous timeout after that boundary is treated as potentially dispatched. The current interface has no explicit dispatch-marker method, so a future contract change or narrowly scoped marker must be owner-approved; no route is wired in this PR. `ReleaseUndispatchedAsync` must be used only when the caller can durably prove the provider request was never initiated/handed off. Client cancellation (including Chat cancellation), timeout, socket error, or worker loss alone is not proof; the method must reject a dispatched/unknown/finalized reservation.
- After any dispatched provider attempt—including a failed provider response—record known actual provider cost idempotently, subtract the estimate from the **original** reserved buckets, and add actual to those same user/workspace/global buckets. If actual exceeds estimate or cap, record the factual full amount and block later admissions; never discard provider liability or refund customer credits.
- If actual is unknown, keep the full estimate reserved, set the reservation to reconciliation-required, and increment the singleton global unknown count. Do not admit any public-free request while the global unknown count is nonzero. Reconciliation may replace the estimate with authoritative actual exactly once, on the original windows, and clear the global hold in the same transaction.
- A proven-undispatched release reverses spend reservation once, but keeps the accepted-message anti-abuse count consumed. Finalization/release/reconciliation share the same lock order and state machine; concurrent release and outcome must have exactly one winner. A periodic lease expiry is never sufficient release evidence.
