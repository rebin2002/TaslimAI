# TASLIM.AI Provider Production-Readiness Recommendation

**As of:** 2026-09-24
**Scope:** Voice, music, and movie/video generation providers for a paid TASLIM.AI product.

## Executive recommendation

TASLIM.AI should **not select or enable one universal provider**. The documented production choice is a staged, provider-neutral trial:

1. **Voice:** run Azure AI Speech and Google Cloud Text-to-Speech as the enterprise Arabic baseline. Run ElevenLabs and Cartesia as specialist realtime/expressive challengers. Treat Kurdish, especially Sorani and Kurmanji, as a hard acceptance gate rather than inferring it from generic multilingual claims.
2. **Music:** run Stable Audio API and Mubert API in parallel. Prefer Stable Audio when deterministic generation controls, downloadable files, audio transformation, and clearer output assignment matter most. Prefer Mubert when long tracks, streaming, webhooks, personalization, and product/UGC embedding matter most.
3. **Movie/video:** start with Runway Dev as the first direct integration candidate; benchmark Google Veo for premium quality and continuity; evaluate Luma for multi-keyframe, extension, interpolation, and video-to-video workflows. Add Kling only after direct schema and quota validation. Keep fal.ai and Replicate as explicitly labelled fallback/benchmark adapters, not as substitutes for direct-provider rights.
4. **Commercial gate:** obtain written vendor and legal confirmation before exposing paid-user output. The required confirmation covers end-user access, SaaS embedding, downloads, caching, resale or white-label use, output ownership or license scope, attribution, prohibited uses, voice/face consent, retention, training use, data residency, rate limits, indemnity, service levels, and termination portability. This report makes no legal guarantee.
5. **Engineering gate:** no broad code change is required for an initial one-provider-at-a-time trial. Before real video enablement, fence movie execution writes with the shared generation-job concurrency token and test stale-worker recovery. Clean duplicate OpenAI voice registrations before voice enablement.

**Quality caveat.** A provider's published language count, “natural” positioning, model label, or latency claim is not an independent quality benchmark. Any quality conclusion not directly stated by a cited provider is an **evaluation hypothesis** to be tested with native-speaker review and controlled latency measurements.

## Evidence labels and pricing method

The report uses three labels:

- **Published fact** — directly stated in the cited provider documentation, pricing, API reference, or terms.
- **Derived calculation** — arithmetic from a published unit price and an explicit assumption; it is not a vendor quote.
- **Unknown / vendor confirmation required** — not established by the reviewed public material, or dependent on a plan, region, model route, or contract.

For voice comparisons, the normalized example assumes **150 words per minute** and **5 billable characters per word including spaces**, or **750 characters per minute**. The examples exclude free tiers, taxes, discounts, retries, egress, storage, and preprocessing. For track- or generation-priced music, a per-minute number is shown only when a documented duration permits a transparent calculation. For video, 30 seconds means one request where the documented model supports it, or three 10-second shots where the model is limited to 10 seconds. Failed-generation billing is excluded unless a provider contract says otherwise.

### Voice trial acceptance test

Use identical MSA, Iraqi, Gulf, and Levantine samples. Include diacritics, names, numbers, dates, code-switching, difficult consonant clusters, punctuation, and long-form prosody. Native Arabic reviewers should score pronunciation, intelligibility, naturalness, dialect appropriateness, and voice consistency. Measure p50/p95 time-to-first-audio, chunk cadence, interruption, reconnect, cancellation, and concurrent-request behavior. Test Sorani and Kurmanji separately. A generic “Arabic supported” result does not satisfy a Kurdish launch requirement.

### Movie continuity and orchestration rule

No reviewed provider documents a universal deterministic scene graph or guaranteed identity lock across a feature-length sequence. The practical continuity hypothesis is to create a canonical continuity pack for every character and location, approve still keyframes first, and prefer extension, video-to-video, first/last-frame, and reference-image workflows over unrelated prompts. Each shot should persist provider, model/version, prompt, negative constraints, seed when accepted, reference IDs, duration, aspect ratio, resolution, audio flag, callback nonce, estimated cost, retry count, and output hash. Native audio should be reserved for approved shots because it increases cost and makes replacement edits harder.

## Architecture compatibility and code-change decision

The repository already has the right provider-neutral primitives for a staged trial.

### Existing compatibility

- **Shared durable jobs:** `apps/api/Generation/GenerationJobExecution.cs` and `apps/api/Domain/Entities.cs` provide database-backed jobs, atomic claiming, lease renewal and recovery, cooperative cancellation, idempotency, concurrency fencing for shared job updates, safe errors, usage, and generic outputs. The lifecycle is suitable for all three domains.
- **Private output path:** `apps/api/Assets/GeneratedAssetPublisher.cs`, `apps/api/Files/FileProcessingService.cs`, and `apps/api/Controllers/AssetsController.cs` keep generated output private behind stored files and authenticated asset access. Provider URLs should be copied into TASLIM storage before a job is marked complete.
- **Voice:** `apps/api/Voice/VoiceGenerationProviders.cs` defines a bounded `GenerateAsync` result containing audio bytes, MIME/format, optional duration/sample rate, and internal usage. `apps/api/Voice/VoiceGenerationJobHandler.cs` selects a server-side provider and publishes an audio asset. This accommodates Azure, Google, ElevenLabs, or a buffered Cartesia adapter without changing the user contract.
- **Music:** `apps/api/Music/MusicGenerationJobHandler.cs` and `apps/api/Music/MubertMusicGenerationProvider.cs` use a synchronous outer contract while hiding create/poll/download. The shape accommodates Stable Audio, Mubert, or a similar one-output provider. It does not expose callbacks, remote cancellation, resumable retrieval, native progress, or stems/multiple outputs.
- **Movie/video:** `apps/api/Movies/MovieEntities.cs` defines `IMovieVideoProvider` with submit, status, retrieve, and cancel. `apps/api/Movies/MovieVideoExecution.cs` persists provider key, operation ID, status, attempts, polls, progress, next-poll time, and completion. This is already suitable for Runway, Veo, Luma, Kling, or Firefly-style asynchronous APIs. No real movie provider is registered; `UnavailableMovieVideoProvider` remains the safe default.

### Required hardening before real video

`MovieVideoExecutionStore` writes in `apps/api/Movies/MovieVideoExecution.cs` visibly update execution and clip rows without requiring the shared `GenerationJob` concurrency token. A recovered claim could therefore leave a stale movie handler racing with the new handler. Before enabling a real video provider, add or verify token-fenced submission, status, cancellation, failure, and ready writes, then test expiry recovery while the stale handler continues. This is a provider-neutral durability requirement.

Before voice enablement, remove duplicate OpenAI voice HTTP-client and provider registrations in `apps/api/Program.cs`. This is registration hygiene, not a blocker to provider neutrality. Keep provider keys, credentials, model IDs, and pricing snapshots server-side. Do not expose provider URLs, keys, or model internals in browser DTOs.

**Code-change decision:** no broad provider rewrite is justified for the first trial. Implement one adapter at a time behind the existing interfaces. The only clearly necessary pre-video code change is concurrency-token fencing and its regression coverage. Any interface expansion for streaming voice, music stems, callbacks, or multi-output video should follow measured product requirements rather than speculative capability.

## Staged trial and release gates

### Stage 0 — Contract and safety gate

Obtain the vendor confirmations listed below. Confirm target region, model/version, rate limits, quota-increase process, billing treatment for failed/cancelled work, output URL lifetime, retention, training use, and incident contact. Establish a cost ceiling and a kill switch. Keep all provider flags disabled until this gate is approved.

### Stage 1 — Voice bake-off

Run identical Arabic and English fixtures through Azure, Google, ElevenLabs, and Cartesia where contractually permitted. Add Amazon Polly as a low-cost control. Score native-speaker pronunciation, intelligibility, dialect fit, prosody, names, numbers, code-switching, first-byte latency, cancellation, reconnect, and concurrency. Treat Sorani and Kurmanji as separate tests. Select a primary only after the quality score, p95 latency, operational behavior, and written rights all pass.

### Stage 2 — Music paid proof of concept

Run Stable Audio and Mubert in parallel using instrumental, loop, long-form, and product/UGC cases. Verify generated duration, format, download retention, failed-generation behavior, retries, caching, and actual billed usage. Add Loudly or SOUNDRAW only if their API license clearly permits paid-user output. Store output hashes and pricing snapshots with each job.

### Stage 3 — Movie shot benchmark

Run 10–20 representative TASLIM shots through Runway Gen-4.5, Google Veo Standard/Fast, and Luma Ray3.2, then add Kling after direct schema validation. Measure identity continuity, camera adherence, temporal artifacts, audio replacement cost, p50/p95 completion time, failure rate, retry rate, output retrieval reliability, and effective cost. Use first/last frames and continuity packs. Test cancellation and stale-worker recovery before enabling any paid-user path.

### Stage 4 — Controlled enablement

Enable exactly one approved provider per domain behind server-side configuration, workspace-level quotas, cost guardrails, safe error mapping, and incident logging. Copy outputs into TASLIM storage, verify MIME/type, byte count, duration, resolution, and hash, and only then publish the asset. Keep a tested fallback disabled until voice identity, pronunciation, music style, or video continuity are shown to be acceptable across providers.

## Vendor confirmation questions

1. Does the plan permit TASLIM.AI to expose generated audio or video to authenticated end users, cache it, retain it, download it, include it in a paid SaaS subscription, and provide API-like or white-label access?
2. Who owns generated output, and what license is granted to TASLIM and its users? Are standalone downloads, synchronized works, catalog distribution, Content ID, and monetization covered?
3. Is attribution required? Are there watermark, provenance, synthetic-voice, disclosure, or platform-specific obligations?
4. What prohibited-use, political, education, religious, healthcare, child-directed, public-figure, face, voice, and copyrighted-input restrictions apply to TASLIM's scope?
